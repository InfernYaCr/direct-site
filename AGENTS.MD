# AGENTS.md — правила работы с проектом

Проект — статический Astro-сайт для оффера «Умный Навигатор»: бесплатная 30-минутная диагностика рекламы для владельцев стоматологий. Сайт должен быстро объяснять боль, показывать конкретную пользу диагностики и переводить человека в заявку через Telegram/VK.

Главная цель: не «красивый лендинг вообще», а понятный конверсионный сайт для клиник, которые уже тратят деньги на ВК или Яндекс.Директ и не понимают, где теряют заявки.

## Текущий продукт

- Название: «Умный Навигатор».
- Оффер: бесплатная диагностика рекламного кабинета за 30 минут.
- Аудитория: владельцы и управляющие стоматологий, особенно клиники с имплантацией, винирами, ортодонтией, All-on-4 и другими дорогими услугами.
- Боль: бюджет уходит на клики, охваты и случайные заявки, а в расписании нет платежеспособных пациентов.
- Обещание: показать, где утекают деньги, посчитать экономику пациента и дать понятный первый план исправлений.
- Основной CTA: оставить заявку на диагностику.
- Каналы связи: Telegram, VK, email поддержки.

Не возвращай проект к старому AI QA tripwire-контексту. Файлы `README.md` и `AI_QA_PROJECT_PLAN.md` могут содержать устаревший или битый текст, но фактическая текущая ветка и код сайта — про стоматологический маркетинг.

## Тон и позиционирование

Пиши по-русски, прямо и предметно. Тон: уверенный маркетолог-практик, который говорит с собственником клиники на языке денег, заявок, кабинета, администраторов и расписания.

Хорошие формулировки:

- «Покажу, где рекламный бюджет уходит в случайный трафик».
- «Считаем не клики, а стоимость пациента и записи в кресло».
- «30 минут по вашему кабинету: кампании, аудитории, заявки, следующий шаг».
- «Без обязательств работать дальше».
- «Сначала разбираем текущий кабинет, а не просим еще месяц бюджета на тесты».

Избегай:

- гарантий результата без условий: «точно приведем 50 пациентов», «удвоим прибыль»;
- неподтвержденной статистики;
- давления страхом без практического выхода;
- общих фраз агентств: «комплексный digital-маркетинг», «индивидуальный подход», «продвижение под ключ»;
- медицинских обещаний и формулировок, которые могут выглядеть как обещание результата лечения.

## Конверсионная логика

Каждый главный блок должен отвечать на один вопрос посетителя:

1. Hero: «Это про мою проблему?»
2. Боль: «Где именно я теряю деньги?»
3. Решение: «Что будет сделано на диагностике?»
4. Метод: «Почему это не очередной общий аудит?»
5. Автор/доверие: «Почему этому человеку можно показать кабинет?»
6. Оффер: «Что я получу и почему сейчас бесплатно?»
7. FAQ: «Есть ли обязательства, риски и что нужно от меня?»
8. Финальный CTA: «Как оставить заявку?»

CTA должен вести к заявке или к якорю блока диагностики. Не плодить второстепенные CTA, которые уводят от заявки.

## Дизайн-направление

Текущий стиль: светлый медицинско-агентский лендинг с теплым фоном, крупной типографикой, темными и светлыми карточками, зелено-синими диагностическими акцентами и оранжевыми CTA.

Сохраняй:

- крупные секционные заголовки;
- много воздуха, но без пустой декоративности;
- визуалы, связанные со стоматологией, аналитикой, рекламным кабинетом и планом действий;
- читаемые карточки, особенно на мобильных;
- сильный первый экран: боль, выгода, CTA и человеческий/медицинский образ;
- restrained visual style: сайт должен выглядеть как серьезная услуга для клиник, а не как инфопродукт.

Не добавляй:

- случайные градиентные шары, абстрактные SVG и декоративный шум;
- темную тему на весь сайт;
- анимации, которые мешают чтению;
- hero без реального визуального сигнала продукта/ниши;
- карточки внутри карточек без необходимости.

## Архитектура проекта

Стек: Astro, статическая генерация, минимум JavaScript.

Важные файлы:

- `src/pages/index.astro` — порядок секций главной страницы.
- `src/components/landing/` — секции лендинга.
- `src/components/Header.astro` и `src/components/Footer.astro` — навигация и футер.
- `src/layouts/BaseLayout.astro` — SEO, OG, schema.org, cookie banner, общие скрипты.
- `src/data/site.ts` — оффер, контакты, FAQ, списки, тексты, ссылки.
- `src/styles/global.css` — дизайн-система и адаптив.
- `public/images/` — изображения.
- `public/downloads/` — скачиваемые материалы, если они нужны.

Повторяющиеся тексты, ссылки, тарифы/офферы, FAQ и контакты держи в `src/data/site.ts`. В компонентах оставляй только разметку и секционные тексты, если они уникальны для блока.

## Правила разработки

- Следуй существующей структуре и CSS-паттернам.
- Для статических секций используй `.astro` компоненты.
- JS добавляй только для реального поведения: меню, cookie banner, простая аналитика, анимации появления.
- Не добавляй тяжелые библиотеки ради простых эффектов.
- Проверяй адаптив от 360px до desktop.
- Не ломай якоря `#pain`, `#inside`, `#program`, `#author`, `#pricing`, если на них завязана навигация.
- Не хардкодь реальные счетчики, токены, ключи платежей и приватные данные.
- Placeholder-ссылки вроде `https://t.me/your_username` замени только когда пользователь дал реальные данные.

## Контент и SEO

Для главной страницы обязательны:

- один H1;
- внятный title и description;
- canonical;
- Open Graph image;
- schema.org для услуги;
- понятная структура заголовков;
- внутренние ссылки на юридические страницы и контакты.

SEO-кластеры проекта:

- реклама стоматологии;
- Яндекс.Директ для стоматологии;
- ВК реклама стоматологии;
- заявки на имплантацию;
- пациенты на виниры / ортодонтию / All-on-4;
- аудит рекламного кабинета;
- стоимость пациента в стоматологии;
- маркетинг стоматологической клиники.

SEO не должен размывать главную: если нужен длинный информационный материал, лучше отдельная страница, а главную держать сфокусированной на заявке.

## Юридическая и этическая аккуратность

Не обещай гарантированное количество пациентов, прибыль, окупаемость или прохождение медицинской модерации. Можно говорить о целях, гипотезах, диагностике, расчетах и вероятных точках роста, если это подано как план проверки.

Для запуска нужно заменить placeholders:

- домен в `astro.config.mjs` / `SITE_URL` / `src/data/site.ts`;
- Telegram, VK и email;
- реквизиты продавца;
- юридические страницы;
- ссылки CTA;
- реальные изображения и OG, если текущие временные;
- счетчики аналитики и цели.

Не помогай со спамом, обходом банов, массовыми рассылками и серыми рекламными механиками. Предлагай безопасные альтернативы: официальная реклама, ретаргетинг, партнерские размещения, контент, добровольная заявка.

## Команды

Установка зависимостей:

```bash
npm install
```

Если `npm install` падает с `ECONNRESET`, можно использовать зеркало:

```bash
npm install --no-audit --registry=https://registry.npmmirror.com/
```

Разработка:

```bash
npm run dev
```

Сборка:

```bash
npm run build
```

Preview после сборки:

```bash
npm run preview
```

В `package.json` сейчас нет `check`-скрипта. Не требуй `astro check`, пока он не добавлен в проект.

## Проверка перед завершением задачи

Для значимых правок проверь:

- `npm run build` проходит;
- первый экран читается на desktop и mobile;
- CTA виден без поиска;
- мобильное меню открывается и закрывается;
- тексты не налезают друг на друга;
- изображения загружаются;
- блок диагностики понятен без дополнительных объяснений;
- юридические ссылки в футере не сломаны;
- в `git status` нет случайных файлов из `dist/` или временных артефактов.

Если проверку выполнить не удалось, честно напиши, что именно не проверено и почему.

## Работа с git

- Не делай `git reset --hard` и не откатывай чужие изменения без явной просьбы.
- Перед переключением веток проверяй `git status --short --branch`.
- Если есть локальные правки пользователя, сначала предложи `git stash` или работай поверх них аккуратно.
- Коммиты делать только по просьбе пользователя.
- Коммит должен быть атомарным и в формате вроде `feat(scope): ...`, `fix(scope): ...`, `docs(scope): ...`.

## Приоритеты Codex

Если конфликтуют красота и конверсия, выбирай конверсию без визуальной неряшливости.

Если конфликтуют SEO и ясность оффера, главную держи ясной, а SEO расширяй отдельными страницами.

Если конфликтуют скорость MVP и идеальная архитектура, выбирай быстрый чистый MVP, который легко продолжить.

Если пользователь просит «посмотри сайт», проверяй не только код, но и фактическую страницу через dev/preview, когда это технически возможно.
